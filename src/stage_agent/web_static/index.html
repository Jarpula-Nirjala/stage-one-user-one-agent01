◆ Lifecycle Agent Programme

One User, One Agent

Every viewer receives a dedicated agent that chooses one measurable goal, decides what to change (or to do nothing), acts within a strict latency budget, is checked by an independent verifier, and is judged against a randomized holdout.

Evidence with provenanceIndependent verificationSafe degradationRandomized holdoutHonest measurement

Built for viewers in smaller cities and towns

Most visits are short: a viewer opens the app, scrolls and leaves. One agent per viewer decides, in seconds, what to change, or whether to leave them alone, and later proves whether it helped.

How it works

The decision loop

01

Understand the viewer

Every fact carries its source, time and freshness. Conflicts between profile, app setting and campaign link are resolved by explicit precedence and kept visible.

02

Choose one goal

One measurable goal from the catalogue, with a deadline and a success signal, or an explained abstention. Unmeasurable goals are never chosen.

03

Decide and act in time

A personalised home page, one proportionate message, or nothing, inside a 60 second budget with at most 8 model and 20 tool calls.

04

Verify independently

A separate verifier checks eligibility, dialect, availability, consent, quiet hours, frequency, copy and holdout, and can reject any action.

05

Degrade safely

When the model or the data store fails, a circuit breaker and cached facts keep decisions fast and safe. A smaller action beats a late or wrong one.

06

Prove the impact

Intention-to-treat on randomized arms with confidence intervals. The biased served-versus-rest comparison is shown only for contrast.

When things fail

The degradation ladder

1Everything healthyFacts + model second opinion + personalised page + proportionate message
2Model slow, down or garbledSafe parse, one retry for bad JSON, circuit breaker; rules choose the goal, same page
3Queue wait above 8 sOptional model call skipped; decision still personalised
4Data store slow or downRead capped at 1.5 s; day-old snapshot; minimal page; no goal committed; no message
5Queue wait above 25 sOnly the minimal safe in-dialect page
6Verifier rejects the planRepair once with a minimal page; drop a failing message; keep what passes
7Nothing safe or on timeNo action, recorded with its reason. A late or wrong action is never published

Who is trusted

Trust boundaries

Untrusted input

  • catalogue descriptions
  • search queries, deeplinks
  • model output
  • phone clocks
  • profile snapshot (a day old)
➜

Gatekeepers

  • scanner, then description discarded
  • one strict deeplink pattern
  • JSON schema + claim check
  • sent−occurred, received_at
  • freshness and precedence rules
➜

Trusted core

  • rule engine
  • independent verifier
  • consent / cap ledgers
  • arms table (holdout)
➜

Effects

  • actions.jsonl
  • viewer state + journal
  • outcomes, learnings
  • reports

Text from the data is content, never instruction. A model answer is a claim: it is accepted only if the rule engine independently finds the goal eligible and its evidence resolves. The reason text it writes is ignored.
